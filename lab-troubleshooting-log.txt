Date/Time: 17 June 2026 / 13:51 BST
Component: VirtualBox 7.x / Windows Server 2022 VM Creation

Error Message:
"Windows cannot find the Microsoft Software License Terms. Make sure the installation sources are valid and restart the installation."

Symptoms:
The Windows Server 2022 setup environment boots normally, but immediately halts with a pop-up error dialog box upon clicking "Install Now" or while setup is starting. The installation cannot proceed further.

Root Cause Analysis:
Oracle VirtualBox automatically attempts an "Unattended Installation" by default when a Windows ISO is detected. It attaches a virtual floppy/auxiliary ISO (`Unattended-...-aux-iso.viso`) containing an automated configuration script. Windows Server setup reads this automated file, conflicts with the unattended script instructions, and fails to parse the licensing terms.

Resolution Steps:
1. Powered off the stalled virtual machine.
2. Deleted the corrupted virtual machine and completely removed its virtual hard disk files from storage.
3. Initiated the creation of a new Virtual Machine in VirtualBox.
4. Selected the Windows Server 2022 ISO file and explicitly checked the option to "Skip Unattended Installation" (or left "Proceed with Unattended Installation" unchecked depending on VirtualBox version wizard UI).
5. Allocated sufficient hardware resources (4096 MB RAM, 2 vCPUs, and 50 GB Virtual Hard Disk).
6. Booted the new VM and manually advanced through the standard Windows Server OS installation wizard successfully.

Status: Resolved / Closed

Error Message: "Keyboard failure ... Failed to change keyboard parameter. Could not send all scan codes to the virtual keyboard (VERR_PDM_NO_QUEUE_ITEMS)."

Root Cause Analysis: The VirtualBox hypervisor's internal virtual keyboard input queue became desynchronized from the physical host machine's hardware input driver, causing the input buffer queue to flood and lock up. 2. Closed the main Oracle VM VirtualBox Manager application on the host machine.

4. Relaunched the VirtualBox Manager application and powered on the Windows Server 2022 VM.

5. Input functionality successfully re-synchronized, allowing a standard login pass.

6. Logged into the Administrator account and provided an explanatory comment to clear the Windows Shutdown Event Tracker prompt triggered by the forced backend process termination.

Status: Resolved / Closed

Component: Active Directory Users / Account Lockout Tasks

Error Message: "The user name or password is incorrect" (Kept saying this over and over again instead of locking out) and "The syntax of this command is:" (When the command prompt failed).

Symptoms: 
1. The keyboard and screen completely froze up right at the start when trying to use Server Manager.
2. After fixing the keyboard, I tried to log out and spam wrong passwords on the bad-login account more than 30 times, but it just wouldn't lock out. It kept saying the password was wrong.
3. When checking jdoe (John) and bad-login, both profiles looked exactly the same in Active Directory. The "Unlock account" box was there for both, so nothing was actually locked.
4. When I tried to run the command to fix it, the command prompt threw a syntax help error and didn't work.

Root Cause Analysis: 
1. VirtualBox crashed its input queue again because the screen buffer got stuck when swapping between things.
2. New Active Directory domains start with the lockout limit set to 0 by default, which means "never lock out." So spamming it 30 times did nothing. Also, changing the Group Policy doesn't immediately affect the main login screen until you completely restart the server.
3. The "Unlock account" checkbox is just a permanent button in Windows Server 2022, not a sign that it's locked.
4. The first command failed because Windows is super picky about spaces, and typing bad-login/active:no squished together breaks the command format.

Resolution Steps:
1. Closed the frozen VM, saved the state, and went into Windows Task Manager on my laptop to kill VirtualBox Global Interface and VirtualBox Interface to get my keyboard working again.
2. Logged back in as Admin, opened Group Policy Management, edited the Default Domain Policy, and changed the Account lockout threshold from 0 to 5.
3. Opened Command Prompt and ran gpupdate /force to try and force the new rule to work.
4. Logged out and tried to spam the password again, but the login screen was still being stubborn because the server needed a full reboot to apply the policy to the console.
5. Went back into the Admin account, opened Command Prompt, and tried to run net user bad-login/active:no but got a syntax error because of a missing space.
6. Fixed the spacing and ran the exact command: net user bad-login /active:no. It finally said it completed successfully.
7. Opened Active Directory Users and Computers, clicked on Standard Users, and verified that Wrong Password now has a little black down-arrow on its icon, showing it's officially locked down and disabled.

Status: Resolved / Closed
